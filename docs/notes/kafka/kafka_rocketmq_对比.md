## 🔄 一、推拉模式对比

### 1.1 核心结论

| 角色 | Kafka | RocketMQ |
|------|-------|----------|
| **Producer → Broker** | Push（生产者主动推送） | Push（生产者主动推送） |
| **Broker → Consumer** | **Pull**（消费者主动拉取） | **Pull**（长轮询，SDK 封装成 Push 体验） |

**本质：** 两者在消费端都是 **Pull 模式**。RocketMQ 的 `DefaultMQPushConsumer` 只是在 SDK 内部用长轮询实现了 Pull，再回调用户的 `MessageListener`，让开发者感觉像是 Push。

### 1.2 为什么选择 Pull？

```text
┌─────────────────────────────────────────────────────────────┐
│                     选择 Pull 的核心原因                     │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. 消费者速率差异大                                        │
│     → 不同消费者处理能力千差万别，Pull 让消费者自己控制节奏  │
│                                                             │
│  2. 批量拉取更高效                                          │
│     → 一次 poll() 拉取几百条，减少网络往返                  │
│                                                             │
│  3. 消费者自主管理位点                                       │
│     → 灵活选择从最新/最早/任意位置消费                      │
│                                                             │
│  4. 容错性更好                                              │
│     → 消费者宕机，消息只是堆积在 Broker，不会丢失            │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 1.3 两者 Pull 的差异

| 维度 | Kafka | RocketMQ |
|------|-------|----------|
| 拉取单位 | Partition | MessageQueue |
| 空轮询处理 | `fetch.min.bytes` + `fetch.max.wait.ms` 长轮询 | `brokerSuspendMaxTimeMillis` 长轮询 |
| 位点管理 | Consumer 自主管理 Offset | Broker 管理消费进度（Consumer 定期上报） |
| 编程体验 | 显式 `poll()` | `MessageListener` 回调（内部仍是 Pull） |

## 🔄 二、顺序消费机制对比

### 2.1 核心结论

**要实现顺序消费，两者都必须满足：**
> **一个队列（Partition/MessageQueue）在同一时刻只能被一个消费者实例消费，且在该实例内部只能被单线程处理。**

### 2.2 线程模型对比

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                           顺序消费线程模型                                   │
├─────────────────────────────┬───────────────────────────────────────────────┤
│          Kafka              │              RocketMQ                         │
├─────────────────────────────┼───────────────────────────────────────────────┤
│                             │                                               │
│   P0 ──→ Consumer-0:T0      │   Q0 ──→ Consumer-A 线程池                   │
│   P1 ──→ Consumer-1:T1      │          └── 线程T0 持有 Q0 锁（串行）       │
│   P2 ──→ Consumer-0:T2      │   Q1 ──→ Consumer-A 线程池                   │
│                             │          └── 线程T1 持有 Q1 锁（串行）       │
│   1 Partition = 1 Thread    │   Q2 ──→ Consumer-B 线程池                   │
│   （线程与分区一一对应）      │          └── 线程T2 持有 Q2 锁（串行）       │
│                             │                                               │
│   消费者实例数 ≤ 分区数       │   1 Queue = 1 线程持有锁                     │
│   超过分区数的消费者空转      │   （线程池内串行，池间并行）                  │
│                             │                                               │
└─────────────────────────────┴───────────────────────────────────────────────┘
```

### 2.3 关键差异

| 维度 | Kafka | RocketMQ |
|------|-------|----------|
| 顺序粒度 | **Partition** | **MessageQueue** |
| 线程模型 | 消费者实例内，一个线程对应一个 Partition | 消费者实例内线程池，对单个 Queue 加锁串行 |
| 扩容上限 | 分区数固定，扩容需重建 Topic | 读写队列可在线调整，扩容更灵活 |
| 热点问题 | 某个 Partition 消息量大 → 单线程瓶颈 | 某个 Queue 消息量大 → 单线程瓶颈 |
| 顺序类型 | 只保证 Partition 内有序 | 支持 **全局有序**（一个 Topic 一个 Queue）和 **队列内有序** |

### 2.4 顺序消费的性能瓶颈

```text
场景：3 个队列，2 个消费者实例

Kafka:
  Consumer-0: P0(T0), P2(T2)  ← 2 个线程并行
  Consumer-1: P1(T1)           ← 1 个线程
  总并行度 = 3（等于分区数）

RocketMQ:
  Consumer-A: Q0(T0持有锁), Q1(T1持有锁)  ← 2 个线程并行
  Consumer-B: Q2(T2持有锁)                ← 1 个线程
  总并行度 = 3（等于队列数）

瓶颈：如果 Q0 的消息量占 80%，则 T0 成为全局瓶颈
       即使 Consumer-A 有 100 个线程，Q0 也只能用 1 个
```

## 📦 三、消息堆积处理对比

### 3.1 堆积根因对比

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                        消息堆积根因树                                       │
├─────────────────────────────┬───────────────────────────────────────────────┤
│          Kafka              │              RocketMQ                         │
├─────────────────────────────┼───────────────────────────────────────────────┤
│                             │                                               │
│  ├─ 消费逻辑慢              │  ├─ 消费逻辑慢                                │
│  ├─ 消费线程数不足          │  ├─ 消费线程数不足                            │
│  ├─ 分区数太少              │  ├─ 读队列数太少                              │
│  ├─ 消息体过大              │  ├─ 消息体过大（默认 4MB）                    │
│  └─ 消费异常反复重试        │  ├─ 消费异常反复重试                          │
│                             │  ├─ Tag 过滤陷阱 ⭐（RocketMQ 特有）         │
│                             │  │   客户端过滤导致无效拉取                    │
│                             │  ├─ 重试队列隐式堆积 ⭐（RocketMQ 特有）      │
│                             │  │   %RETRY%Group 队列堆积 millions           │
│                             │  └─ 顺序消费单线程瓶颈 ⭐（RocketMQ 特有）    │
│                             │      Orderly 模式严格单线程                   │
│                             │                                               │
└─────────────────────────────┴───────────────────────────────────────────────┘
```

### 3.2 紧急止血方案对比

| 方案 | Kafka | RocketMQ |
|------|-------|----------|
| **扩容消费者** | 消费者数 ≤ 分区数，分区固定难扩容 | 消费者数 ≤ 读队列数，**读写队列可在线调整** |
| **跳过堆积** | `kafka-consumer-groups.sh --reset-offsets --to-latest` | `mqadmin resetOffsetByTime -s now` |
| **调整消费线程** | 消费者实例内多线程（但一个分区一个线程） | `setConsumeThreadMin/Max` 热调整 |
| **临时关闭顺序消费** | 改为非顺序消费（分区级无序） | 改为 `MessageListenerConcurrently`（队列级无序） |
| **批量消费** | `max.poll.records` | `setConsumeMessageBatchMaxSize` |

### 3.3 特有陷阱与解决方案

#### Kafka 特有：分区数固定，扩容困难

```text
问题：分区数 = 4，消费者已经扩到 4 个，Lag 仍不下降

解决路径：
  1. 增加分区（需要重建 Topic 或使用 Kafka 的增分区命令）
     → 新消息进入新分区，旧分区堆积仍需老消费者处理
  2. 用 Flink/Spark Streaming 批量读取（绕过消费者组，开几百并行度）
  3. 影子消费组：新消费组用更高并发追平，再切换
```

#### RocketMQ 特有：Tag 过滤陷阱

```text
问题：消费者订阅 "*"，在 consumeMessage 里用 if-else 过滤
       → Broker 推送全量消息，Consumer 拉取后丢弃 90%
       → 有效消费速率极低，Lag 持续堆积

✅ 正确：consumer.subscribe("Topic", "TagA || TagB")  // Broker 端过滤
❌ 错误：consumer.subscribe("Topic", "*")            // 客户端过滤

解决：如果 Tag 种类太多，直接拆 Topic，不要用 Tag 做精细过滤
```

#### RocketMQ 特有：重试队列隐式堆积

```text
问题：原 Topic Lag 正常，但系统吞吐极低
       → 查看 %RETRY%ConsumerGroup 发现堆积 millions
       → 消费者在反复重试"毒消息"

RocketMQ 重试间隔：
  第 1 次：10 秒
  第 2 次：30 秒
  ...
  第 16 次：2 小时

解决：
  1. 消费逻辑里捕获异常，超过重试阈值返回 CONSUME_SUCCESS
  2. 设置 consumer.setMaxReconsumeTimes(3)  // 默认 16，建议调小
  3. 紧急清空重试队列：mqadmin resetOffsetByTime -t %RETRY%Group -s now
```

#### RocketMQ 特有：消费超时触发 Rebalance

```text
问题：单条消息处理超过 15 分钟（consumeTimeout 默认）
       → Broker 认为消费者挂掉，触发 Rebalance
       → 消息重新分配，导致重复消费和堆积加剧

解决：
  1. consumer.setConsumeTimeout(5)  // 缩短超时
  2. 异步化：消费线程只做消息入队，业务线程异步处理
```

### 3.4 架构级优化对比

| 优化手段 | Kafka | RocketMQ |
|---------|-------|----------|
| **分层消费** | 核心/非核心拆 Topic + 不同 Consumer Group | 核心/非核心拆 Topic + 不同 Consumer Group |
| **预处理减负** | Kafka Streams / ksqlDB 过滤聚合 | 无原生流处理，需借助外部框架 |
| **弹性伸缩** | K8s HPA（Lag 指标） | K8s HPA（Lag 指标），队列调整更灵活 |
| **背压限流** | 生产者令牌桶限流 | 生产者令牌桶限流 |
| **采样降级** | 消费端动态采样率 | 消费端动态采样率 |
| **冷热分离** | Tiered Storage（分层存储） offload 到 S3 | 无原生分层存储，需手动归档 |
| **亿级堆积清空** | Flink/Spark 批量读取，重置 Offset | Flink/Spark 批量读取，重置 Offset |

## 🏗️ 四、架构定位与适用场景

### 4.1 核心差异

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                                                                             │
│    Kafka = 流平台（Stream Platform）                                        │
│    RocketMQ = 金融级消息中间件（Message Queue）                             │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 4.2 详细对比

| 维度 | Kafka | RocketMQ |
|------|-------|----------|
| **设计定位** | 分布式流处理平台 | 金融级消息队列 |
| **核心优势** | 高吞吐、可回溯、生态丰富 | 低延迟、功能全、运维友好 |
| **典型吞吐** | 百万级 TPS | 十万级 TPS |
| **消息持久化** | 持久化到磁盘，可配置保留时间 | 持久化到磁盘，支持同步刷盘 |
| **消息回溯** | 支持任意 Offset 回溯 | 支持按时间/Offset 回溯 |
| **事务消息** | 支持（Kafka Transactions） | **原生支持，更成熟** |
| **延迟消息** | 不支持原生，需借助外部 | **原生支持 18 个级别** |
| **死信队列** | 需手动实现 | **原生 DLQ 支持** |
| **消息轨迹** | 需借助外部（如 Kafka Streams） | **原生支持消息轨迹追踪** |
| **消息过滤** | 无 Broker 端过滤 | **Broker 端 Tag/SQL 过滤** |
| **多副本同步** | ISR 机制 | 同步双写 / Dledger 自动切换 |
| **跨语言客户端** | 极丰富（Java/Go/Python/JS...） | 主要 Java，其他语言较弱 |
| **云原生支持** | Strimzi / Confluent Operator | Apache RocketMQ Operator |

### 4.3 适用场景

| 场景 | 推荐 | 原因 |
|------|------|------|
| 用户行为日志、埋点数据 | **Kafka** | 吞吐高，可回溯做离线分析 |
| 实时计算（Flink/Spark Streaming） | **Kafka** | 生态无缝集成 |
| 事件溯源（Event Sourcing） | **Kafka** | 日志持久化，可重复消费 |
| 订单状态变更、支付通知 | **RocketMQ** | 事务消息、延迟消息、死信原生支持 |
| 秒杀库存扣减 | **RocketMQ** | 低延迟，顺序消费支持好 |
| 金融交易、对账 | **RocketMQ** | 同步刷盘，消息轨迹，金融级可靠性 |
| 定时任务、延时队列 | **RocketMQ** | 原生 18 级延迟消息 |
| 跨语言微服务通信 | **Kafka** | 客户端生态更丰富 |

## 📝 六、一句话总结

> **Kafka 是"流"，追求的是吞吐和生态；RocketMQ 是"队列"，追求的是可靠和功能完备。** 两者在消费端本质上都是 Pull，顺序消费都受限于队列/分区的单线程处理，但 RocketMQ 在消息功能（事务、延迟、死信）和运维灵活性上更胜一筹，Kafka 在流处理和生态广度上无可替代。
